# Parent Manager: architecture

Status: proposal for review, 2026-11-07. [vision.md](vision.md) is the source of truth for scope, and [spec.md](spec.md) defines how Phase 1 behaves, [spec-phase2.md](spec-phase2.md) how Phase 2 (calendar and documents) behaves, and [spec-phase3.md](spec-phase3.md) how Phase 3 (tasks and chores) behaves. This document describes how we build it, and [backlog.md](backlog.md) breaks the work into Phase 1 items. Decisions that need the product owner are marked **Decision** and collected in [decisions-needed.md](decisions-needed.md).

## 1. Where we start

PR #1 already delivered:

- **App:** an Expo SDK 58 app with TypeScript and Expo Router, building for iOS and Android.
- **Bundle ID:** `com.myparentmanager` on both platforms. The first choice, `com.parentmanager.app`, was already registered with Apple by someone else.
- **Supabase:** a client and the CLI project folder, linked to the hosted project `parent-manager` in us-east-1.
- **EAS:** the project `@abhinav08/parent-manager`, with development, preview and production build profiles.
- **Tooling:** ESLint and Prettier, Jest, a Maestro smoke test, and GitHub Actions running CI on every PR and E2E on `main`.
- **Protection:** `main` requires a PR and passing CI, for admins too.

Gaps against the fixed stack:

- **Environments:** one Supabase project serves every environment (F-03).
- **Monitoring and payments:** Sentry, PostHog, RevenueCat and Resend aren't added yet.
- **Session storage:** the session is stored unencrypted (F-08).

### Challenges to the fixed stack

The stack holds up. Three gaps need an addition or a decision, not a replacement:

1. **Offline sync.** The stack has no piece for offline data with conflict handling. Supabase Realtime pushes live changes but doesn't keep an offline copy, so we add a sync library (section 5).
2. **An AI provider.** Recipe import needs a large language model (LLM) that can read images. It isn't in the stack, so it's a **Decision** (section 6).
3. **pnpm.** It works with Expo, and new Expo projects use pnpm's `hoisted` mode. pnpm's stricter default mode can break native module resolution in React Native, so F-02 keeps `hoisted`. No reason to change the choice.

### Navigation

- **Bottom tabs,** in the order Plan, Calendar, List, Tasks, Household (Calendar is Phase 2, FR2-CAL-1; Tasks took the Recipes slot in Phase 3, D-29, FR3-TASK-1). Bottom tabs keep the main actions in thumb reach. Recipes is a button in the Plan tab's header, and its screens (`/plan/recipes/...`) are in the Plan stack, so back returns to the plan; S-11 still searches every recipe.
- **One main action per screen,** placed at the bottom: add a meal, add an item or import.
- **Bottom sheets for secondary flows** instead of full-screen pushes, so a parent who gets interrupted keeps their place.
- **Tab shell:** `src/app/(tabs)/_layout.tsx` uses Expo Router's headless tabs (`expo-router/ui`) with the design system's `FloatingTabBar`, so the bar is drawn from tokens rather than styled on top of a native tab bar. Each tab is a folder (`plan/`, `calendar/`, `list/`, `tasks/`, `household/`), so a feature can add its own stack later. Tab screens use `Screen`, which pads scrolling content by `layout.tabBarClearance` plus the bottom safe area. `/` redirects to `/plan`.
- **Component gallery:** `/gallery` shows every shared component, with switches for light, dark and the largest text size. It's a protected route that exists only in development builds, opened from the Household tab.

### Deep links

- **Links:** the app's link scheme for development, plus universal links (iOS) and App Links (Android) on the product domain. These handle invitations and, later, meal-train links.
- **Domain:** this needs a domain. **Decision:** the product name and domain.

## 3. Data model

All tables live in Postgres. Every table holding household data has `household_id`, `created_at`, `updated_at` (set by the server) and `deleted_at` (a soft-delete marker, which sync needs). Primary keys are UUIDs that the client can generate, so a row can be created offline.

### 3.2 Phase 1 entities

#### Catalog

These tables are global and read-only, filled from versioned seed data:

| Table              | Key columns                                                                                                                                                                                                           | Notes                                                                                                                                                  |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `units`            | `id` (such as `unit.cup_us`, `unit.cup_metric`, `unit.tbsp_au`, `unit.g` or `unit.each`), `dimension` (`mass`, `volume` or `count`), `to_base` (factor to g, ml or each), `systems`                                   | Each unit with a regional size gets its own ID: US cup 236.6 ml, metric cup 250 ml, Australian tablespoon 20 ml, US pint 473 ml, imperial pint 568 ml. |
| `store_sections`   | `id` (such as `section.produce` or `section.dairy`), `default_order`                                                                                                                                                  |                                                                                                                                                        |
| `ingredients`      | `id` (such as `ingredient.milk`), `household_id` (null for catalog items, set for a household's own items), `default_dimension`, `density_g_per_ml` (optional), `section_id`, `allergen_codes[]`, `is_default_staple` |                                                                                                                                                        |
| `ingredient_names` | `ingredient_id`, `locale`, `name`, `plural`, `synonyms[]`                                                                                                                                                             | `en-US` "zucchini", `en-GB` "courgette", `en-AU` "zucchini".                                                                                           |

Unit, section, tag and allergen names live in the app's locale files. Ingredient names live in the database, because the catalog grows without app releases.

How the catalog is built (R-01.1):

- **Reference rows are read-only.** Anyone, including the anonymous role, can read `units`, `store_sections` and catalog rows of `ingredients` and `ingredient_names` (where `household_id` is null). Only migrations write them.
- **Units.** `to_base` matches `src/i18n/units.ts`. `regions` says which size a plain word such as "tbsp" means in each region (`unit.tbsp_au` in AU). `unit.pinch` and `unit.dash` have no `to_base` (R-ING-5). `unit.floz_imperial` (28.41 ml) is there for UK and AU recipes.
- **Household ingredients** have IDs of the form `ingredient.h.<uuid as 32 hex digits>`, made on the device so they work offline, and can't be default staples. Parents and family members write them; caregivers read them. Removing one is a soft delete.
- **Household ingredients sync through `household_ingredients` (R-02.2).** "Add as new ingredient" must work offline, and `ingredients` can't join the sync layer (text IDs, catalog rows), so the device writes a synced `household_ingredients` row (name, locale, section, dimension). A trigger publishes it to `ingredients` and `ingredient_names` as `ingredient.h.<the row's UUID as hex>`. The outbox sends writes in order, so the ingredient exists before any recipe line that uses it.
- **The catalog on the device.** `src/features/ingredients/catalog.ts` bundles the seed file, and `useIngredients(locale)` builds the name index from it plus the household's rows, so pickers, search and allergen checks work offline. New catalog rows reach the app with the next release.
- **`ingredient_names` carries `household_id` too,** kept equal to its ingredient's by a trigger, so its policies need no join.
- **Seed data (R-01.2).** `supabase/catalog/ingredients.json` is the source of truth for catalog ingredients: section, default dimension, density, allergen codes, staple flag, and per-locale name, plural and synonyms. Each locale lists the other regions' names as synonyms where that word means nothing else locally, so a UK recipe's "courgette" resolves in a US household. `node scripts/catalog-seed.js --new` turns it into a new seed migration that upserts every row and soft-deletes dropped ones. `pnpm run catalog:check` (in CI) validates the JSON, including that no word names two ingredients in a locale, and fails if the newest seed migration is out of date.
- **Matching on the device (R-01.3).** `src/features/ingredients/matching` is pure TypeScript. `buildNameIndex` folds a locale's names, plurals and synonyms (catalog and household) into an index of IDs. `searchIngredients` serves pickers and typed list items. `parseIngredientLine` reads "1½ cups whole milk, warm" into a quantity, a unit for the household's region and an ingredient ID, with a match quality for review. Unit words, number words and plural endings are in the locale files under `ingredientParser`. Display text is only ever matched through the index; everything after it compares IDs.
- **Allergen codes** are a fixed list checked by the database and mirrored in `src/features/ingredients/catalog-ids.ts`, with section IDs.

#### Recipes

| Table                | Key columns                                                                                                                                                                                                                                                         | Notes                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `recipes`            | `id`, `household_id`, `title`, `servings`, `prep_minutes`, `cook_minutes`, `tags[]`, `notes`, `source_type` (`manual`, `url`, `photo`, `screenshot`, `text`, `voice` or `library`), `source_url`, `library_recipe_id`, `content_locale`, `created_by`, `updated_by` | Titles and steps are user content and are never translated. Tags are fixed IDs such as `tag.no_cook`. |
| `recipe_ingredients` | `id`, `household_id`, `recipe_id`, `position`, `ingredient_id`, `quantity`, `unit_id`, `quantity_base`, `raw_text`, `note`, `optional`                                                                                                                              | `raw_text` keeps the original line ("2 cups whole milk, warm") for review and future re-parsing.      |
| `recipe_steps`       | `id`, `household_id`, `recipe_id`, `position`, `text`                                                                                                                                                                                                               |                                                                                                       |

How recipes are stored (R-02.1):

- **Synced.** All three tables use `private.enable_sync()` (section 5), and the app registers them in `src/features/recipes/tables.ts`. Each line and step is its own row. Deleting a recipe tombstones its lines and steps on the server, so they sync too.
- **Server-set values.** The server records `created_by` and `updated_by`, and works out `quantity_base` (R-ING-3): quantity times the unit's `to_base`; a count ingredient with no unit counts each; anything else (no quantity, "a pinch", "salt to taste") is null. `src/features/recipes/quantity.ts` does the same on the device, so offline lines show the same.
- **Checks.** Lines and steps must belong to a recipe of their own household, and a line's ingredient must be the catalog's or the household's own. A line or step added offline to a recipe deleted meanwhile arrives deleted. A recipe has at most 100 lines and 50 steps (FR-REC-4).
- **Writes.** Parents and family members write recipes; caregivers read them.
- **Scaling and allergens on the device (R-03.2).** Recipe detail scales base quantities by the servings ratio and shows a unit of the household's system as written, or converts one of the other system (`src/features/recipes/scale.ts`). The allergen notice compares ingredient allergen codes with the household's people's allergy codes. People aren't in the sync layer yet, so detail fetches them and keeps the last list in memory for the session (cleared on sign-out). Offline with no list, it says the check couldn't run.
- **Tags (R-02.3).** The fixed FR-REC-7 set is stored as IDs in `recipes.tags` (checked by the database) and named from `recipes.tags.*` in the locale files; `tagNameKey`, `hasTag` and `NEEDS_DEFROSTING_TAG` (`tag.needs_defrosting`, for N-02.2's "defrost tonight") live in `src/features/recipes/tables.ts`. Tags are matched by ID only, never by their names.
- **Deleting (R-02.3).** Recipe detail offers deleting to parents and family members. The confirmation says how many live plan entries from the current week on use the recipe (FR-REC-11). `planRecipeDeletion` (`src/features/recipes/delete.ts`) turns every live entry that plans it into free text with the recipe's title, then tombstones the recipe, all through the outbox, so it works offline. The server does the same for writes the deleting device never saw: a trigger snapshots entries still pointing at the recipe when it's deleted, and an entry added or changed offline to plan a deleted recipe arrives as free text (migration `20261115100000_recipe_deletion.sql`).
- **The starter library isn't in these tables.** It ships with the app as versioned seed data per locale (R-04.1), so it works offline and is read-only by construction. It lives in `src/features/recipes/starter/library.ts` with `STARTER_LIBRARY_VERSION`: catalog ingredient and unit IDs, and titles and steps per locale, falling back to en-US. Today's five recipes are placeholders the team wrote; the real content is R-04.2 (decision D-8), and its rights get recorded there. "Save a copy" writes an ordinary household recipe with `source_type` `library` and the starter's ID in `library_recipe_id` (FR-REC-3).

#### Planner

| Table                 | Key columns                                                                                                                                               | Notes                                                       |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `plan_entries`        | `id`, `household_id`, `date`, `slot` (`breakfast`, `lunch`, `dinner`, `snack` or `drink`), `recipe_id` or `free_text`, `servings`, `leftover_of_entry_id` | A week is a date range, so it needs no separate week table. |

How the plan is stored (P-01.1):

- **Synced.** `plan_entries` and `plan_entry_portions` use `private.enable_sync()` (section 5), and the app registers them in `src/features/planner/tables.ts`. A delete is a tombstone, so a delete by one partner wins over a move by the other. Removing an entry tombstones its portions on the server.
- **Dates, not moments.** `date` is a Postgres `date`: the calendar day in the household's timezone. A clock or timezone change never moves an entry, and changing the week start only regroups the display.
- **Entries.** A household recipe or free text, servings in quarter steps (a baby plate is ¼), and `position` for order within a slot, which can hold several entries (FR-PLAN-4). A starter recipe is saved as a household copy before it's planned. The recipe and the "leftovers of" entry must be in the entry's household.
- **Portions.** One row per entry and person (a unique index): 0, ½, 1 or 2, or a baby plate at ¼ (FR-PLAN-6). The app derives the row's ID from the entry and person IDs (`portionId`), so two partners setting the same portion offline write one row.
- **Writes.** Parents and family members write the plan; caregivers read it.
- **The week on the device (P-01.2).** `src/features/planner/week.ts` does date arithmetic on `YYYY-MM-DD` dates as whole UTC days, so weeks cross month ends and daylight-saving changes exactly. Only "today" depends on a timezone: the household's (`Membership.timezone`), falling back to the device's. S-10 reads entries from the local copy. Allergen markers use the household's people, fetched online and kept in memory for the session like recipe detail's, with each person's portion on the entry or their R-SERV-1 default.
- **Adding (P-01.3).** S-11 searches household and starter recipes with R-03.1's `searchRecipes`, and lists recently planned recipes first. Planning a starter saves a household copy first (or reuses an existing copy of it), because entries reference household recipes only. Servings default to the people's R-SERV-1 portions, rounded up to ½. Planner events go through F-07.2's `track` from `@/lib/analytics`.
- **Undo (P-01.4).** A delete is a final tombstone, so removing an entry is held back rather than reversed: `useUndoable` hides the entry at once and writes the delete when the 5-second undo bar goes. Undo just drops the held change. Leaving the screen writes whatever is held. Duplicating copies the entry's portion rows too.
- **Portions (P-03).** An entry with no portion rows follows each person's R-SERV-1 default. Saving portions in S-12 writes a row for every person (0 means not eating; rows are never deleted) and sets the entry's servings to their sum (R-SERV-2). Servings can still be set directly afterwards, and `servings` is always the number the list scales by. `entryLineQuantities` in `src/features/planner/plan.ts` turns an entry into base quantities per recipe line, for the list engine (G-01.1).
- **Copy last week (P-02).** `planWeekCopy` moves each of last week's entries by 7 whole days to the same weekday and slot, after what stays in each slot, and keeps leftover links only between copied entries. Copies include portion rows. "Replace" writes the copies at once and holds back removing this week's old entries behind the undo bar; undo removes the copies instead.
- **Leftover links (P-04).** An entry can be "leftovers of" a live entry that comes before it (an earlier day, or an earlier slot the same day) in its own week or the week before (FR-PLAN-8). `src/features/planner/leftovers.ts` checks this and lists the candidates for the long-press sheet. Linking makes the entry take on the earlier entry's recipe or text, since it's the same food, and keeps its own servings. The list engine already applies R-SERV-3 (`effectiveServings`): the original is scaled by both entries' servings and the leftovers need nothing. Unlinking, or removing the original, gives the entry its own ingredients again. A move that breaks a link clears it in the same change. The server (migration `20261115110000_leftover_links.sql`) drops any link that doesn't hold rather than refusing the write, so offline links and moves still sync: the target must be live, earlier and at most 13 days before (the widest window either week start allows), and moving an entry drops links to it that no longer hold. Links never point forward, so they can't loop.
- **Week planned (P-06).** Dinners planned are the days of the week with at least one live dinner entry, shown as "N of 7 dinners planned". `week_planned` is recorded when this device's own change takes the week from under 5 to 5 or more (FR-PLAN-12), once per week per device: the weeks already recorded are kept in the `expo-sqlite` key-value store, keyed by household ID and week start. A partner's synced change doesn't record it, so it comes from the device that planned the week.

### How the grocery list is built

The list is built from plan entries in the chosen date range. For each recipe ingredient:

1. Scale the quantity by servings and portions.
2. Group by ingredient and dimension (mass, volume or count).
3. Sum the base quantities.
4. Pick a friendly display unit for the household's unit system.
5. Remove the item if the pantry marks it `have` or as a staple.

The rules for keeping user edits:

- **Regenerating** replaces items that came from the plan, but never items the user edited or checked.
- **Manual items** are never touched.
- **Different dimensions stay separate.** Volume and mass lines for the same ingredient become separate entries unless the ingredient has a density. Wrong merges are worse than duplicates.

The engine is a set of pure TypeScript functions with no side effects, unit-tested and run on the device, so it works offline.

- **What the plan needs (G-01.1).** `weekNeeds` in `src/features/grocery/engine.ts` takes every plan entry (so leftover links to other weeks resolve, R-SERV-3), the recipes and lines, ingredient facts (`buildIngredientFacts`: dimension, density and section from the bundled catalog and household ingredients) and the week's pantry. It returns one need per ingredient and dimension, keyed `<ingredient ID>|<mass, volume, count or none>`, with its summed base quantity and the entry and line behind each part, plus the staples and "have" ingredients it left off. Mass and volume merge only through the catalog's `density`. A no-quantity line ("to taste", a pinch) becomes a `none` need, and only when nothing measured of that ingredient is needed. Results are sorted by key, so every device gets the same output. `itemDisplayParts` applies the household's unit system for display only.
- **Keeping user edits (G-01.2).** `reconcileList` in `src/features/grocery/reconcile.ts` compares the needs with the list's rows and returns sync writes plus an added, changed and removed summary (FR-LIST-3). Each generated item keeps `plan_quantity_base`, how much of the plan's need it covers. Checked items and items a member deleted keep covering theirs and never change, so more eggs after a check-off is a new item for the difference, and a deleted item returns only for a rise since the deletion. A user-modified item keeps its quantity, takes the rest of the need and its sources, and gets `plan_changed`. Unchecked, unmodified items take the rest of the need or are deleted with `plan_quantity_base` 0, so a later need brings them back. Manual items never change, except that two manual rows of one ingredient merge (R-LIST-5). Rows it creates get IDs from `stableId` (a version 8 UUID from the list, the group and the group's row count), so two devices recalculating offline write the same rows (NFR-OFF-5).
- **Tables and the weekly list (G-01.3).** `grocery_lists`, `grocery_items`, `grocery_item_sources` and `purchase_events` (migration `20261114100000_grocery.sql`) are synced, with `checked` as the items' check column, so a check-off records who and when and a stale uncheck can't clear it (FR-LIST-8). Every member reads and writes them (spec section 2.2); triggers keep each row in its list's household, refuse non-members before looking at other rows, and tombstone an item's sources with it. `purchase_events` takes `recorded_by` from the writer, at most one live event per item (R-MEM-1). The pantry joins sync in the same migration (`version` added, its own `updated_at` trigger dropped), so staples and "have" are on the device. A week's default list has the ID `weekListId(household, week start)`, the same on every device. `GroceryListKeeper`, mounted with the tabs, runs `weeklyListUpdates` whenever the plan, recipes, pantry or list rows change: it creates a week's list once the week has a planned recipe or is open in the List tab (FR-LIST-2), recalculates every list from this week on, and leaves past weeks alone. It waits for the first load and for any pull to finish, so it never works from half a household, and records `list_generated`.
- **The List tab (G-02.1).** S-13 (`src/features/grocery/list-screen.tsx`) shows the current week's default list from the local copy. `buildListView` (`view.ts`) groups live items by store section in the catalog's default order, sorts unchecked items by name with the locale's collator, and moves checked items to the collapsed "in the cart" group (FR-LIST-4). Rows show the quantity in the household's unit system, or the unit a member chose (`display_unit_id`), the number of planned meals behind the item, and an inline allergen notice from the household's people, fetched like recipe detail's (R-LIST-8). Checking off is one `update` of `checked` through the sync layer (FR-LIST-8). Opening the tab marks its week open (`useOpenListWeek`), so the keeper creates the list; the keeper's change summaries and "Regenerate" (parents and family only) reach the screen through `list-events.ts` and show as a toast (FR-LIST-3). Rows have test IDs by section and position (`list-item-produce-0`, `list-cart-item-0`) for Maestro.
- **Adding an item (G-02.2).** S-14 (`add-item-sheet.tsx`) searches the locale's ingredient names with `searchIngredients`, or adds the text as typed in a section the member picks (R-LIST-6), with an optional amount and unit. `planAddItem` (`add-item.ts`) decides the write: an ingredient already on the list, unchecked and in the same dimension, gets the amount added (a generated item becomes user-modified, so recalculation keeps it; R-LIST-5); the same ingredient with no amount changes nothing; anything else is a new manual row that keeps the unit as typed in `display_unit_id`. Checked items and no-quantity items are never merged into.
- **Item detail (G-02.3).** Each row has a details button (and a screen reader action) beside its check-off target, which opens S-15 (`item-sheet.tsx`). `detail.ts` holds the rules. An edit writes only what changed and marks the item user-modified, clearing `plan_changed` (FR-LIST-7). A plan item keeps its dimension, since the engine matches it by ingredient and dimension, and a plan item with no quantity can't get one; a manual item can take any unit. Sources list the planned meals and recipe lines behind the item by day and slot (FR-LIST-12). "I already have this" writes a `have` pantry row for the list's week (an ID from `stableId`, so two devices write one row) and removes the item with `plan_quantity_base` 0, so undoing "have" brings a plan item back (FR-PAN-4, FR-PAN-5). Delete is a final tombstone, so it is held behind the 5-second undo bar with the planner's `useUndoable`; a member's deletion keeps the item's `plan_quantity_base`, so the plan only brings it back for more.
- **Pantry and "assumed at home" (G-03.2).** S-22 (`src/features/pantry/pantry-screen.tsx`, opened from the Household tab) shows "at home this week" (this list week's `have` rows) and the live staples by store section; `pantry.ts` holds the rules. Undoing "have" tombstones the row, and since "I already have this" removed the plan item with `plan_quantity_base` 0, the keeper puts it back (FR-PAN-5). Removing a staple sets it to `hidden_staple` rather than deleting it, and adding a hidden staple turns it back on (R-PAN-1). New staple and "have" rows get IDs from `stableId`, so two devices write one row; a tombstone keeps its ID for good, so `insertStable` moves on to the next index when the device already holds that ID (marking "have" again after an undo). Caregivers see staples read-only, and RLS refuses their staple writes (FR-PAN-6). The list's collapsed "assumed at home" row lists `weekNeeds(...).staples` for the week, minus ingredients already on the list, and one tap adds a staple as a manual item (FR-PAN-3, R-PAN-3).
- **Shopping together (G-04.1).** Check-offs use the sync layer's check column, so the server records `checked_by` and `checked_at` and a stale uncheck can't clear a newer check (FR-LIST-8). `grocery_items.updated_by` (migration `20261116100000_grocery_updated_by.sql`) is stamped by a trigger with whoever wrote the row, never the client, and is cleared on account deletion. The List tab shows "checked by <member>" (the row's avatar and screen-reader label) once the household has more than one member; names come from `fetchMembers` when online and are kept in memory only. `usePartnerActivity` (`use-shopping.ts`, rules in `shopping.ts`) shows the "someone else is updating the list" banner for 60 seconds after another member's write: on first look it uses the server's `updated_at` (never later than now), and after that any row whose version moved on and was written by someone else counts as changed now, timed on the device, so clock skew can't keep the banner up (FR-LIST-9). `test-utils/sync/harness/grocery.harness.ts` covers two partners on the real tables: a check-off reaches the partner within 2 seconds, both shopping offline converge, and a stale offline uncheck never undoes a newer check (NFR-OFF-5).
- **Purchase events and finish shopping (G-04.2).** `purchase_events` joins the sync layer. Checking an item off writes its event (ingredient ID or, for free text, just the item ID; base quantity; time; `checked_off`) unless the item already has a live one, and unchecking within 10 minutes of the purchase tombstones it (FR-LIST-8, FR-MEM-1, R-MEM-1); rules in `purchases.ts`. Event IDs come from `stableId` over the item (`insertStable` skips IDs the device already holds), so two partners checking the same item off offline write one event. Migration `20261116110000_finish_shopping.sql` makes the server keep any other second live event for an item as a tombstone instead of failing the unique index, so neither device stalls. "Finish shopping" asks for confirmation, writes `confirmed` events for checked items without one, and sets `grocery_items.shopped_at`, which the server stamps with its own time and never changes again (FR-LIST-10). Shopped items stay live and checked, so the list engine still counts what was bought; the List tab leaves them out, and unchecked items stay. Events come only from these in-app actions (FR-MEM-2). `shopping_finished` carries only counts.
- **Frequently bought (G-09).** `frequentlyBought` (`frequent.ts`) works suggestions out on the device from the synced purchase events, so they work offline: ingredients bought at least twice in the last 56 days, ranked by count and then the most recent purchase, at most 8 (R-MEM-2, FR-MEM-3). It leaves out ingredients unchecked on the current list, staples, and ingredients hidden with "don't suggest" (R-MEM-3). Free-text items have no ingredient ID to count across lists, and names are never matched as text, so they aren't suggested. The add item sheet shows them before anything is typed, and hides the section for a household with no history; one tap adds one (`suggestion_frequent`, `frequent_suggestion_used` with its rank). "Don't suggest" writes `frequent_suggestion_hides` (migration `20261116120000_frequent_suggestion_hides.sql`, synced, one live row per ingredient with a `stableId`), whose `hidden_until` the server sets to 90 days from the last hide (FR-MEM-5). Every member can hide a suggestion, since every member adds items.

### 3.3 Data minimization for children

- **Store age bands, not birth dates.** Children are stored as `household_people` with an age band such as `expecting`, `infant_0_6m`, `infant_6_12m`, `toddler`, `preschool` or `older_child`.
- **No photos, health records or full names are required.** A nickname is enough.
- **Due month only (D-6).** Onboarding asks "Expecting, or how old is your youngest?". An expecting person has `due_month` as `YYYY-MM` text, which can't hold a day, and the database refuses it for any other age band. Nobody not yet born gets allergies or diets.
- **Fixed codes.** `person_dietary` accepts only the allergen codes in `catalog-ids.ts` and the diet codes in `src/features/people/codes.ts`. Removing a person soft-deletes their codes with them.
- **Onboarding is one transaction.** `complete_onboarding()` creates the household, its people and their codes together, so an interrupted onboarding never leaves a household without its answers. Until then the answers stay in the on-device draft (FR-ONB-7).
- **Allergies and pregnancy status are health-related data.** UK GDPR and some US state laws, such as Washington's My Health My Data Act, treat this kind of data strictly, so legal review must cover it before launch.

### 3.4 Data export and account deletion coverage

Export (A-04.2) and deletion must cover every table that holds household data. Add a row here with each new table.

**Deletion registry (A-04.3).** Deletion doesn't rely on foreign-key cascades alone. Every column that ties a row to a household or a user is registered in `private.deletion_registry`, in the migration that creates the table:

```sql
select private.register_for_deletion('public.recipes', 'household_id', 'household');
select private.register_for_deletion('public.recipes', 'created_by', 'user', 'set_null');
```

- **Deleting a household** (`private.erase_household`) deletes every row registered against it, newest registration first, then the household. Leaving as the only member, account deletion and FR-PRIV-7 all use it.
- **Deleting an account** (`private.erase_user`) deletes the user's own rows (`delete`), clears the user from shared rows that stay with the household (`set_null`, shown as "former member"), then deletes the auth user, which removes their sessions and identities. It fails, changing nothing, if a registered column still holds the user's ID afterwards.
- **While erasing,** `auth.uid()` reads as null and `private.is_erasing()` is true, so triggers that stamp the current user or guard a column can't put the ID back.
- **`supabase/tests/data_deletion.test.sql` fails** if a public table has a `household_id`, a foreign key to `auth.users` or `households`, or a uuid column named `*_by` or `*user_id` that isn't registered.
- **Export registry (A-04.2).** Export works the same way: every table that holds household or user data is registered in `private.export_registry` in the migration that creates it, with `private.register_for_export('public.<table>', 'household' | 'user' | 'none', '<key column>', omit_columns, reason)`. `household` tables go in the household export (rows whose key column is the household), `user` tables in the account export (rows whose key column is the member), and `none` needs a reason. `supabase/tests/data_export.test.sql` fails if a public table with a `household_id`, a foreign key to `auth.users` or `households`, or a `*_by` / `*user_id` column isn't registered. `public.export_household_data(target)` (parents only) and `public.export_account_data()` read the registry, leave out deleted rows and omitted columns (secret hashes), and return JSON by table; nothing reads entitlements, so export is free (FR-PAY-10). The app (`src/features/account/export.ts`, on S-30) writes a ZIP with a manifest, a JSON file per table and CSV files for recipes, plans and lists (`src/lib/zip.ts`, stored entries, UTF-8 names), puts it in the cache and opens the share sheet (`expo-sharing`, `expo-file-system`). It needs a connection and is off offline (NFR-OFF-2). Analytics get the scope and a size bucket only. A household export also holds each ready document's files in `documents/<document_id>/<page>.<ext>` (A-05, FR2-PRIV-1): the app asks the `documents` function for read links one document at a time (D-22), streams the ZIP to a file with `ZipWriter` so a large vault never sits in memory, lists the files and any document deleted mid-export in the manifest, and deletes the ZIP and its downloads when the share sheet closes and on sign-out. A failed read stops the export rather than leave a document out.
- **Backups (FR-PRIV-4).** Deleted rows leave the live database at once. They stay in Supabase's daily backups until those expire (7 days on Pro, 14 on Team, up to 30 on Enterprise), so the promise is 30 days at most, and the plan chosen in D-1 must keep it. Point-in-time recovery, if it's turned on, must keep a window of 30 days or less. The privacy policy states this period (L-01.2).

Sign-out does the server update if this device shared any; leaving or removal is the server trigger from B-01.1. ## 4. Row-level security and household isolation

- **RLS on every table,** with no exceptions. The anonymous role gets no access except to `app_config` and catalog reads.
- **Membership checks.** A `SECURITY DEFINER` helper function, `private.household_role(household_id)`, returns the caller's role or null (also null for family members and caregivers while the household is on Free, so a lapse pauses their access), and runs with a fixed search path. Policies use it as `using (private.household_role(household_id) is not null)` for reads, and test the role for writes. Membership rows are cached per statement through `(select auth.uid())`, the pattern Supabase recommends for performance.
- **Child tables carry `household_id` too.** For example `recipe_ingredients` and `grocery_items` have their own copy, so policies avoid joins, and a trigger checks it matches the parent row.
- **Privileged actions go through RPCs.** Creating a household (`create_household`, which makes the caller its first parent), accepting an invitation, removing a member, transferring ownership and deleting an account run as Postgres RPCs or Edge Functions that check the role explicitly. Clients can never insert into `household_members` or `household_entitlements` directly.
- **Premium limits are enforced on the server too.** A trigger, or the invite RPC, rejects a third adult or a caregiver seat without an active entitlement. The app's gating is only for the user experience.
- **Invitations.** `create_invitation` returns a 6-character code and a link token once; only their SHA-256 hashes are stored (`code_hash`, `token_hash`), and clients can't select either column. `preview_invitation` and `accept_invitation` take a code or a token and return a `status` (`ok`, `invalid`, `rate_limited`, `revoked`, `used`, `expired`, `premium_required`, `already_member`, `in_other_household` or `seat_limit`) instead of raising, so a wrong attempt is recorded in `invite_attempts` rather than rolled back. Accepting locks the household row and re-checks the seats, so two acceptances can't both take the last seat. The Premium seat cap is `app_config` key `household.premium_seats` (6 if unset). `revoke_invitation` is for parents.
- **Members.** `change_member_role` and `remove_member` are for parents. Role changes keep the seat rules (2 parents; family and caregiver seats need Premium and fit the cap) and never leave the household without a parent (FR-HH-14). Removing sets the member's `status` to `removed`, so `household_role()` refuses them at once; leaving yourself is `leave_household`, which sets `left`. The last parent can't leave while anyone else is a member, even a paused one (FR-HH-14); the only member's leaving deletes the household and everything that cascades from it (FR-HH-8). `membership_status()` tells a signed-in user whether they're a `member`, `paused` (a family member or caregiver while the household is on Free), `removed` or have `none`, which RLS alone can't, so the app can show S-35.
- **Storage.** Private buckets use paths of the form `<household_id>/...`, with storage policies that check membership of the first path segment. Images for recipe import are never stored: they go to the import function in the request body (section 6).
- **Per-row visibility (Phase 2).** Events and documents add a second check after membership: `private.can_read_event(id)` (a parent, or `shared` for family and caregivers) and `private.can_read_document(id)`. Child tables (`event_people`, `event_reminders`, `event_exceptions`, `event_documents`) follow their parent. pgTAP tests cover each role with and without a share, and storage policies get the same tests (NFR2-SEC-1).
- **Tests.** pgTAP tests in `supabase/tests` create two households and assert that every table is invisible and unwritable across them, for each role. They run in CI against a local Supabase stack (F-04).

## 5. Real-time sharing, offline sync and conflicts

**Goal:** the grocery list, the weekly plan (and later the calendar) work fully offline, and changes appear on a partner's phone within a couple of seconds when both are online.

**Approach:** keep a local SQLite copy of the household's working data, run all reads and writes against it, queue writes in an outbox, and sync both ways.

**Decided (D-13, 2026-11-08): we build our own.** There's no sync vendor. The pieces:

- **Local copy:** `expo-sqlite` in `src/lib/sync` holds the household's working data and is read on start (H-06.2).

#### How the sync layer is built (`src/lib/sync`)

- **Generic over tables.** A feature registers its table with `defineSyncTable({ name, columns })`. The server table needs the system columns (`id`, `household_id`, `version`, `created_at`, `updated_at`, `deleted_at`). The engine has no feature tables of its own.
- **Local copy (H-06.2).** One SQLite table per registered table, with the system columns and the feature's columns, so features can query it with SQL. `sync_meta` records which household the copy belongs to (another household empties it), each table's column list (a change rebuilds that table and pulls it again) and its pull cursor. All access goes through one queue, because expo-sqlite transactions aren't exclusive.
- **Encrypted.** The file is encrypted with SQLCipher (`useSQLCipher` on the `expo-sqlite` plugin), using a random 256-bit key in SecureStore. A build without SQLCipher keeps no local copy rather than storing it in the clear. Sign-out deletes the file and its key (FR-AUTH-7).
- **Reading.** `SyncProvider` (mounted by the tab layout) opens the copy for the member's household. `useSyncedRows(table)` reads live rows from it, so cached data shows offline and after restarts (NFR-OFF-1).
- **Only with a session (#336).** The copy opens without one, but `SyncProvider` starts Realtime and syncs only while `useAuth()` is signed in, and stops Realtime when the session goes. The Supabase remote checks for a session before every request and never sends one without it (supabase-js would send the publishable key, so it would run as `anon` and get 401). A 401 refreshes the session once, shared by the parallel requests that got it, and tries again; after that the 401 waits like any other.
- **Pulling.** A sync runs on start, on reconnecting and when the app returns to the foreground. The first pull lists the household's live rows. Later pulls fetch rows with `updated_at` at or after the newest one seen, less a 60-second overlap so a late commit isn't missed, including tombstones, in `updated_at`, `id` pages. A row replaces the local one only if its `version` is newer, so repeats and late deliveries are harmless. After 30 days away, the device lists everything again and drops rows the server no longer has (NFR-OFF-6).
- **Local writes and the outbox (H-06.3).** `useSyncWriter()` gives `insert`, `update` and `remove`. Each write is applied to the local copy at once and queued in `sync_outbox`, in order, in the same transaction, so it survives restarts and reboots (NFR-OFF-3). Each row keeps the last row the server sent (its base); what the app reads is the base with its queued writes replayed on top. A pull, a Realtime event or a push response therefore never hides a waiting write, and once the queue drains the row is exactly the server's.
- **Pushing.** Writes go in order: runs of creates on one table in one request, and updates and deletes to different rows up to 8 at a time, so 500 queued changes sync well within 10 seconds (NFR-OFF-4). Each update carries the `version` it was based on. A failed write is handled by why it failed:
  - **Waits:** offline, a 401 while the session refreshes, 408, 429 or a 5xx. It's retried with backoff, however long that takes.
  - **Refused:** RLS (`42501`, for example after the member was removed) or a constraint (`22xxx`, `23xxx`). It leaves the queue at once and the row shows the server's copy again. A count of refused writes is shown to the user (NFR-OFF-6).
  - **Anything else:** dropped after 8 attempts.

  So nothing can stall the queue, which was the spike's S6 failure. A create retried after a lost response finds the row already there (`23505`) and completes.

- **Server rules.** `private.enable_sync(table, check_columns)` (migration `20261110100000_sync_rules.sql`) gives a feature table the conflict rules below, through two generic triggers:
  - The server sets `created_at`, `updated_at` and `version`.
  - A tombstone never changes, and a late edit gets the tombstone back.
  - Each check column (such as `checked`) records `<column>_at` and `<column>_by`. A write based on an older `version` can't clear it.

  The function also revokes hard deletes, adds the pull index and publishes the table to Realtime. A feature's migration still writes the table's own RLS policies.

  Erasure for a deletion (section 3.4) is the one exception: while `private.is_erasing()` is true, the update trigger lets the change through, tombstones included, and only bumps `version` and `updated_at`. A feature's own trigger that guards a column (such as keeping `created_by`) must also let erasure through.

- **First load on a new device (A-01.3).** A device that has never pulled the household (no table has a `pulledAt` mark) reports `firstLoad` until its first sync finishes. A table added by an app update doesn't count. Meanwhile `FirstLoadGate` shows a loading state in place of the tabs, which then open on the Plan tab; offline it asks for a connection and offers to try again. Tables are pulled in parallel, with the local store writing one at a time, so a household with 200 recipes loads within 5 seconds on 4G (FR-AUTH-8; checked in `__tests__/sync/first-load.test.ts` with a simulated 150 ms, 5 Mbit/s link).
- **Pending indicator.** `PendingChangesBanner`, above the tab bar, shows how many changes are waiting until they sync, and how many the server refused.
- **Two-device harness.** `test-utils/sync/harness` runs two devices (two users, two SQLite files and two engines) against a local stack, through offline edits, a restart and reconnection, and checks every conflict rule. It includes the spike's S4 and S6 failures as regression cases. It runs as the "Sync harness" CI job (`pnpm run test:sync`).
- **Outbox:** writes are queued in order and survive restarts. The server sets `updated_at` and `version`, and deletes are soft (H-06.3).
- **Realtime:** Supabase Realtime, filtered by household, applies remote changes to the local copy (H-06.4).

How we got here:

| Option                                                   | Result                                                                                                                                                                                                          |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Legend-State with its Supabase sync plugin (tried first) | **Failed** the H-06.1 spike (#27, PR #110). On the device, a row deleted elsewhere came back, and a stale uncheck stalled the write queue. Its Supabase plugin is also a beta.                                  |
| PowerSync                                                | Not tried. It would add a vendor holding a copy of children's data, from about USD 49 a month.                                                                                                                  |
| **Build our own** (an `expo-sqlite` outbox and Realtime) | **Chosen.** No new vendor or processor, full control over the conflict rules below. It costs about 2 to 3 more days, and we own any sync bugs. The spike's two-device test harness is H-06.3's acceptance test. |

### Conflict rules

Most edits are small and touch different rows, so simple rules are enough:

- **Row-level last-write-wins.** The server sets `updated_at`, and `version` increments on every write. Client clocks are never trusted.
- **Granular rows.** List items, plan entries and recipe lines are each their own row, so two partners editing different items never conflict.
- **Check-offs are recorded with who and when.** Two partners ticking the same item end up with it ticked, and an "unchecked" from a stale device can't silently override a newer "checked".
- **Deletes are soft (tombstones),** so a deleted item isn't brought back by an offline device.
- **Regeneration respects user edits** (section 3.2). It runs on one device and writes ordinary rows, so it syncs like any other change.
- **Recipe edits** are last-write-wins for the whole recipe. Recipes are rarely edited by two people at once, and the app shows "updated by <partner>" afterwards.

### Realtime

- **What we subscribe to:** Supabase Realtime database-change events on the household's tables, filtered by `household_id`. Realtime enforces RLS on what each client receives.
- **How (H-06.4):**
  - The engine joins one channel per household (`sync:<household_id>`), with a `postgres_changes` listener per registered table filtered by `household_id`. `private.enable_sync()` adds each table to the `supabase_realtime` publication.
  - An event is applied like a pulled row: only if its `version` is newer, and with queued writes replayed on top. An event missing a column (a large unchanged value) is fetched whole.
  - Each (re)join pulls once, to catch up on what was missed while disconnected.
  - `SyncProvider` listens only while the app is online and in the foreground.
  - The harness measures delivery between two devices against the 2-second p95 target (FR-HH-13, NFR-PERF-3).
- **Removed members:** Realtime checks RLS for every change, through `private.household_role()`, so a removed member stops receiving changes at once, and the harness checks this. When the app next loads membership and finds the user no longer belongs to the household, it deletes the local copy (`resetSync`).
- **Presence:** "Sam is shopping" is optional polish for later.

### Per-row visibility (Phase 2)

Phase 1 tables are visible to every member, so a pull by `updated_at` is enough. Phase 2 events and documents can stop being visible to a member without the row changing for them (unshared, a share removed, a lapse, a removal), so their pulls never see a tombstone, and Realtime sends them nothing (C-01.3, R2-ACC-2, NFR2-OFF-2):

- **Server.** A synced table is marked scoped with `private.enable_scoped_sync('public.<table>')` (registry `private.scoped_sync_tables`). `public.visible_ids(target, household)` runs as the caller, so RLS decides, and returns the IDs of the household's live rows the caller can see now, as one `uuid[]` so PostgREST's row limit can't cut the list short. Other tables are refused (`22023`).
- **Device.** Tables registered with `defineSyncTable({ ..., scoped: true })` are checked against `visible_ids`: local rows the server no longer returns are dropped (unless a write is queued), and visible rows missing locally are fetched, such as an event's unchanged people and reminders when it's shared again. The engine checks on opening, on every Realtime (re)join, and every 60 seconds while connected (`VISIBILITY_INTERVAL_MS`), so an unshared event leaves a caregiver's device within a minute online and right after reconnecting. A failed check (offline) changes nothing.
- The calendar's four tables, the three document tables, busy blocks and the two task tables are scoped. The two-device harness covers unsharing, a lapse and a removal.

## 6. AI recipe import

### Pipeline

1. **Client (S-19, S-20, `src/features/import/`):** the parent picks the input: a link, pasted text, a screenshot or a camera photo. Images (`image.ts`, R-07) are shrunk on the device to 1600 px on the long edge and compressed to JPEG, then sent in the import request itself; see "Images" below. Camera access is asked for on the first "take a photo"; the photo library opens through the system picker, which needs no permission. The app makes the job's UUID itself and keeps it, with the input, on the device (`useImportRun`), so leaving the screen or the app being killed doesn't lose the import: on return it joins the request still in flight, or reads the job row back by ID (importers can read their own jobs) until it finishes or 75 seconds pass. A lost connection does the same, because the server may still finish. The `ai_import` kill switch hides every entry point and sends the import route to manual entry (AI-20).
2. **Edge Function `import-recipe`:** checks the session, then starts a job with `ai_import_start()` under the app's job ID (a reused ID is refused), which refuses caregivers and members over the hourly limit. Right before a parser call it reserves one import with `ai_import_reserve()`, a conditional upsert on the `ai_usage` row, so concurrent requests queue on its lock and can't pass the allowance. `ai_import_finish()` records the outcome, and a failure releases the reservation. These RPCs are callable only by the service role.
3. **Extraction:**
   - **Links:** the server fetches the page with SSRF guards (`fetch_page.ts`): http and https on default ports only, no credentials in the URL, and every resolved address public (no private, loopback, link-local, metadata or IPv6 forms of them). Redirects are followed by hand, at most 3, and each hop is checked again. Pages are HTML only, capped at 2 MB and 10 seconds. The runtime's fetch resolves the host again, so DNS rebinding between check and fetch is a known remaining risk.
   - **Embedded data:** if the page has a complete schema.org `Recipe` (a title, ingredients and steps), it's parsed directly with no LLM call, which is cheaper and exact, and the import doesn't count. Its ingredient lines keep their original text with zero confidence until normalization (R-05.3) matches them to the catalog.
   - **Otherwise** the readable text is extracted (scripts, styles and page furniture removed, capped at 20,000 characters) and goes to the parser like pasted text.
   - **Text:** used as given.
   - **Images:** passed to the LLM's image input from memory. The function checks the type (JPEG or PNG, by its first bytes) and size (about 2 MB at most), and never writes the image anywhere, so it's gone when the request ends (FR-AI-12). This replaces the planned temporary storage bucket: there's nothing to clean up and no bucket that could be left with images in it. The app deletes its compressed copy when the import is saved, discarded or abandoned.
4. **LLM parsing** (R-05.3) with a strict JSON output schema, in `supabase/functions/import-recipe/ai/`:
   - **Provider seam:** `createAiParser` (`ai_parser.ts`) builds one provider-neutral request (`prompt.ts`: instructions, the schema, the user content) and hands it to an `AiProvider` adapter. `ai/select.ts` picks the adapter from the function's secrets: `AI_PROVIDER=anthropic` with `ANTHROPIC_API_KEY` (and optionally `AI_MODEL`) uses Claude (`anthropic.ts`, plain `fetch`, structured output through `output_config.format`); `AI_PROVIDER=fake` uses a deterministic rule-based fake (`fake.ts`) and works only when `SUPABASE_URL` is a local stack (there, links on the reserved `.test` domain get canned pages from `fake_pages.ts`, for E2E); anything else leaves imports failing with `import.parser_unavailable`, uncounted. Adding a provider is one adapter file and one line in `select.ts`.
   - **Output:** title, servings, times, steps, and ingredient lines with the original text, quantity, unit ID, ingredient name, note and confidence, plus suggested tags and allergens the source mentions. `validate.ts` checks every field again: units, tags and allergens must come from the fixed lists (`vocabulary.ts`, kept equal to the app's by a Jest test), numbers are range-checked, and lines with no amount or an inferred ingredient have their confidence capped.
   - **Inputs:** only the source content, the household's `locale` and `region`, the regional unit words and the allowed lists (AI-8, AI-15). The source sits inside `<source>` tags as data (AI-9).
   - **Retry:** invalid output, a rate limit, overload or a network error is retried once after 1 second (AI-18); a refusal, a bad key or a non-recipe fails at once. Output is capped at 8,000 tokens per call, the per-job cost ceiling.
5. **Normalization on the device** (`src/features/import/normalize.ts`), when the review screen opens:
   - **Why on the device:** the matcher (R-01.3), the bundled catalog and the household's own ingredients already live there, and the recipe editor uses the same code, so imported and typed lines match the same way. The server never needs the household's ingredient list.
   - **Ingredients:** the model's ingredient name and the original line are both run through `parseIngredientLine`; the better match wins. Anything unmatched becomes a new household ingredient (section "other") when the recipe is saved.
   - **Units:** the model's unit ID, already checked on the server; lines from embedded page data are parsed on the device.
   - **Confidence:** the model's confidence, capped by how the match was found (exact 1, partial 0.85, fuzzy search 0.5, none 0). Lines below 0.7 or unmatched are highlighted (FR-AI-6).
6. **Review (always, S-21, `src/features/import/review-screen.tsx`):** the draft opens in the recipe editor (S-18) with review extras. Nothing is saved before the user confirms.
   - Each line shows the source's original text. Low-confidence lines and unmatched ingredients are highlighted with a text tag, and also marked "not checked for allergens" (AI-13).
   - Allergens are matched on the device from the catalog against the household's allergy profiles (AI-11); allergens the source itself mentions add to them. Matches get the import-review AllergenNotice with the disclaimer at the top, and the affected lines are marked. The notice can't be dismissed, and doesn't block saving.
   - Saving writes through the sync layer with `source_type` `url` or `text` and the link (FR-AI-15). Discard asks first. "Enter manually instead" opens the editor prefilled with the title and the raw text in notes (FR-AI-13).
   - The form and the review highlights are kept on the device (`useDraftState`) until saved or discarded, so the app being killed loses nothing.
7. **Cleanup:** there's no stored image to delete (see Images). The job row keeps the draft and metadata for support and quality evaluation for 30 days, then is purged.

### Voice

Voice import is out of the MVP. The vision lists it, but it adds speech-recognition plumbing. Pasted text covers the same need for now.

### Usage limits

- **Monthly allowance per household (D-9):** 5 on Free and 100 on Premium (its fair-use cap), per calendar month in the household's timezone.
- **Rate limits:** 10 import attempts per member per rolling hour, and a hard ceiling on cost per job (R-05.3).
- **Server settings:** all of these live in `app_config` under `ai_import.limits`, read on every request, so they're tuned without a release.
- **What counts:** only successful parses count against the allowance. Embedded schema.org imports that need no LLM call are free, and never reserve.
- **Housekeeping:** a `pg_cron` job every 10 minutes fails jobs stuck processing for over 2 minutes (releasing their reservation) and purges job records older than 30 days (NFR-SEC-9).
- **The app's view:** `ai_import_allowance()` returns used, total and the reset date for the import screen (FR-AI-2, FR-AI-10).

### Privacy

- **What the model sees:** only the recipe content. Never household names, people or allergy profiles; allergen matching happens after parsing, in our own code.
- **Provider terms:** the provider must not train on our data and must keep it for a short retention period. **Decision:** which provider.

### Quality

The evaluation set in `ai-eval/` (R-05.4) has 60 original recipes, 20 each in US, UK and Australian formats, as text, links, screenshots and photos, with a hand-made gold parse. `ai-eval/run.ts` runs them through the real pipeline and scores ingredient, unit and allergen accuracy and hallucinated lines against spec AI-22. CI runs it with the fake provider on every build and compares the report with `ai-eval/results/fake.json`; `pnpm run eval:ai` runs it against a real provider once there's a key (see `ai-eval/README.md`).

### Apple Reminders format (G-06.1 decision)

The G-06.1 spike checked EventKit and `expo-calendar` 58 (`ExpoCalendar.createReminder`, `listReminders` and `ExpoCalendarReminder.update`). EventKit has no public API for Reminders' sections, or for the grocery categories that iOS 17 adds to lists made in the Reminders app. It also can't set the order of reminders: they show in the order they were created. So the export works like this:

- **One list per week.** It's titled like the text export's heading ("Groceries, Nov 15 – Nov 21"), from translations, in the household's locale. It's created in the default Reminders account. The app keeps the list's calendar ID per household and week in on-device storage (`expo-sqlite/kv-store`). If that list was deleted in Reminders, the next export creates a new one (spec, FR-EXP-3 edge cases).
- **One reminder per item, created in the formatter's order.** Sections come first in the List tab's order, then items by name, so a first export reads in aisle order.
  - **Title:** the item's line from the shared formatter ("2 L milk"), which is what Siri reads and the watch shows.
  - **Notes:** the section's name ("Dairy and eggs").
  - **URL:** `<scheme>://list?item=<grocery item ID>`. This is how a re-export finds the reminder again, without matching on display text, and tapping it opens the List tab. The URL holds only a random ID, no names.
- **Re-export.** It reads the list's reminders and matches them to items by the ID in the URL.
  - A new item gets a new reminder at the end, with its section in the notes, because order can't be changed.
  - An item whose line changed (a new quantity) gets its title and notes updated.
  - An item that's been checked off or removed in the app gets its reminder marked completed.
  - A reminder the shopper completed in Reminders stays completed, and reminders without an app URL (added by hand) are left alone.
  - Nothing is ever duplicated or deleted.
- **Rejected options:** a Reminders list per section (it clutters Reminders with several lists a week and can't be grouped), a section prefix in the title ("Dairy: milk" is noisy for Siri and the watch), and deleting and recreating the list on every export (it loses the shopper's completions and causes iCloud sync churn).
- **Native setup:** `expo-calendar` is an Expo SDK module, so no custom native code is needed. Its config plugin sets `NSRemindersUsageDescription` from the locale file, and drops the calendar usage strings (`calendarPermission: false`) because the app never asks for calendar access. Android blocks the plugin's calendar permissions with `android.blockedPermissions`, because Reminders export is iOS only. `ios/` stays generated.

## 8. Free and Premium entitlements (household level)

- **The household is what's entitled,** not the person. `household_entitlements` is the single source of truth, which the app reads through sync, so every member sees Premium the moment it's bought.
- **Billing provider interface (M-01.1, D-10 interim):** the app buys through `src/lib/billing/`, a provider-neutral interface shaped like RevenueCat's `react-native-purchases`: `getOfferings`, `purchasePackage`, `restorePurchases`, `getCustomerInfo`, `logIn` and `setAttributes`, returning the same `Offerings`, `Package` and `CustomerInfo` shapes and RevenueCat's error codes. `EXPO_PUBLIC_BILLING_PROVIDER` picks the implementation:
  - **`mock` (the only one for now):** the mock store. Offerings come from a catalog of PROPOSED placeholder prices (monthly and annual, with the 14-day trial), priced in the device's store currency through the `src/i18n` helpers. Purchases and restores go to the server's mock store, which charges nobody. app.config.ts allows the mock only in development and preview builds and in the local end-to-end build (`billingMockAllowed`); a production build selects no provider whatever the variable says.
  - **`revenuecat` (later):** a second class implementing the same interface by calling the SDK, selected in `getBilling()`. Screens don't change.
  - **Unset:** no provider. Offerings are empty and buying fails with `CONFIGURATION_ERROR`.
- **RevenueCat setup:**
  - **App user ID:** the RevenueCat app user ID is the purchaser's Supabase user ID.
  - **Household attribute:** at purchase, the app sets a RevenueCat attribute `household_id`, which the webhook reads.
  - **Webhook:** the Edge Function `subscription-events` checks the shared authorization header (`BILLING_WEBHOOK_AUTH`, set with RevenueCat in D-10), converts RevenueCat's event to the normalized shape below and applies it. Until that secret exists it refuses every request, and it never accepts mock events.
  - **Reconciliation:** a nightly job compares households with RevenueCat's REST API, behind the `Reconciler` interface in `supabase/functions/_shared/billing/reconcile.ts`. The mock store's reconciler is a no-op.
- **One idempotent path (M-01.2):** every subscription event, from RevenueCat or the mock store, reaches `household_entitlements` through `public.apply_subscription_event(event jsonb)`, which only the service role can call. Events are modelled on RevenueCat's types: `INITIAL_PURCHASE` (a trial start when `period_type` is `TRIAL`), `RENEWAL` (a trial conversion when `is_trial_conversion`), `CANCELLATION` (auto-renew off, Premium kept until the period ends; with `cancel_reason` `CUSTOMER_SUPPORT` it's a refund, which ends Premium at once), `UNCANCELLATION`, `BILLING_ISSUE` (with a grace period, still Premium), `EXPIRATION` and `PRODUCT_CHANGE` (takes effect at the next renewal). Each event is stored once in `subscription_events`, keyed on its ID, so a replay changes nothing; an event older than the last one applied is recorded but not applied. The entitlement records its `source` (`mock` or `revenuecat`) and `store`. `tier` is the only column gates read: `trialing`, `active` and `grace_period` are Premium.
- **The mock store (D-10 interim):** the Edge Function `mock-store` plays the app store for the mock provider. It keeps each store account's subscription in `mock_store_subscriptions` (period start and end, trial, auto-renew, billing issue and grace end, a pending plan switch), creates the events a store would, and applies them through the same path. The store account gets one 14-day trial. A second parent can't buy while the household is Premium. A "delayed webhook" option holds the events for 90 seconds, or until restore, to show the app's "activating" state; restore sends held and latest events again.
  - **Test clock:** `advance` moves a household's subscription to its next renewal, trial end, billing issue (16-day grace), grace end or expiry, so testers see every lifecycle state. `manage` cancels, uncancels, switches plans, refunds or fixes the payment, as the store's settings would.
  - **Safety:** the function refuses every request (`billing.mock_disabled`) unless the Edge Function secret `BILLING_MOCK_ENABLED=true` is set on that project. No migration sets it. The product owner sets it on the hosted test project only; never on a production project. Locally, put it in `supabase/functions/.env` (git-ignored). Production builds never select the mock provider either (above).
- **Every member sees the change (FR-PAY-8):** `household_entitlements` is published to Realtime. The app's `EntitlementProvider` reads the row, listens for changes, and checks again on foreground and every minute while open.
- **Edge Function client:** billing functions call PostgREST and Auth over `fetch` (`_shared/admin.ts`) rather than supabase-js, so a cold worker boots fast.
- **What the app uses:** the RevenueCat SDK on the device is used only to show offerings, purchase and restore. Feature gates read our database, not the SDK.
- **Premium sheet (M-02.1, S-32):** `PremiumSheetProvider` at the root holds the one sheet, and every trigger calls `usePremiumSheet().openPremiumSheet(trigger)`: the invite sheet's family and caregiver roles, the import screen's allowance notice, templates and history (as they're built), and the Household tab's Premium row. After a purchase or restore the sheet shows "activating" until the server entitlement turns Premium (polling every 3 seconds, up to 5 minutes), never trusting the device.
- **Subscription status (M-02.2, S-33):** the Household tab's Premium row opens S-33: the tier, the renewal, trial or end date, the plan (and a pending switch), who bought it, "manage" and "restore purchases". Manage opens the store's `managementURL`, or for the mock store the in-app test store (`/household/mock-store`), which offers the store's settings (turn auto-renew off or on, switch plans, refund, fix payment), the test clock, and a "delay the next webhook" switch. The test store shows only where `billingMockAllowed` is true and the server reports the mock enabled. Only the buying parent manages; the other parent sees who did.
- **Lapse or refund:** `tier` returns to `free` and Premium features pause. Caregivers lose access through RLS on their role and the tier, but their membership rows and all data stay. Nothing is deleted, and export keeps working.
- **The purchaser leaves the household:** the subscription stays with the purchaser's Apple or Google account, and the household keeps Premium until the period ends. The app then prompts a remaining parent to subscribe. Moving a subscription between households is out of scope for the MVP.
- **Trials and restore:** free trials are store-level introductory offers configured in RevenueCat, and restore purchases calls RevenueCat. Products, prices and offerings are set up by the product owner, as a human gate in `CLAUDE.md`.
- **Gates enforced on the server (M-03):** caregiver and family seats (`create_invitation`, `change_member_role`, the seat cap, and pending invitations that wait while the household is on Free), the AI import allowance (`private.ai_monthly_allowance`), saved templates, and history beyond the free window. New gates call `private.household_is_premium(household)`; history uses `private.free_history_start(household)` (the current week and the 4 before it, in the household's timezone and week start) and `private.history_visible(household, day)`. Multiple lists are Premium too, but come after the MVP. Allergy warnings, export, deletion and privacy controls are never gated: `supabase/tests/premium_gates.test.sql` fails if one of their functions or policies reads the tier.
- **History window (G-08):** the read policies of `plan_entries`, `plan_entry_portions`, `grocery_lists`, `grocery_items` and `grocery_item_sources` also require `private.history_visible`, so a free household reads only the current week and the 4 before it, and can't edit older weeks. Nothing is deleted: Premium sees everything again, and the export includes all of it. Because these tables are synced, the app's `HistorySync` calls `SyncEngine.refetch` on a tier change, which pulls them in full (bringing older weeks back, or dropping them from the device after a lapse). The Plan tab shows the history prompt for older weeks, and S-34 (`/plan/history`) lists past weeks read-only. `purchase_events` stay readable, because purchase memory is free.

## 9. Other cross-cutting pieces

### Authentication

Supabase Auth, with:

- **Email:** a one-time code by default, with a magic link as an alternative. Codes are more reliable than links on mobile, because email apps open links in the wrong browser. Supabase sends these emails through Resend over SMTP, from the product domain. Until the domain (D-2) and Resend account (D-4) exist, development and staging use Supabase's built-in email, which is rate-limited. Codes have 6 digits and last 10 minutes, and a new one can be sent every 30 seconds (`supabase/config.toml`). One email template, `supabase/templates/sign-in-code.html`, serves both new accounts (confirmation) and existing ones (magic link). It's generated from the locale files by `pnpm run email:templates`, with a Go template branch on the `locale` saved in the user's metadata at sign-up for any locale whose copy differs, and `pnpm run email:check` (in CI) fails if it drifts. **Wrong codes:** Supabase Auth doesn't count wrong codes per code, so two limits apply. The app stops accepting a code after 5 wrong tries and asks for a new one, which replaces the old code on the server, and the server allows 10 code checks per IP address every 5 minutes, which keeps guessing a 6-digit code out of reach for a client that ignores the app's limit. The config file sets the local stack only: the hosted project's auth settings and templates are set in the dashboard.
- **Apple and Google:** Sign in with Apple and Google sign-in on the device, then `signInWithIdToken`. Apple requires Sign in with Apple when other social sign-ins are offered. **Apple (A-02.1):** on iOS, `expo-apple-authentication` shows Apple's own button and sheet, and the app passes Apple's ID token and the raw nonce to `signInWithIdToken` (Apple gets the nonce's SHA-256). There's no native Apple SDK for Android, so there the button opens Apple's web sign-in through Supabase OAuth in an `expo-web-browser` auth session, which returns to `auth-callback`. That needs a Services ID and key in the Supabase project, so the Android button is hidden until `EXPO_PUBLIC_APPLE_WEB_SIGN_IN=1`. **Same email, one account (FR-AUTH-3):** Supabase links an Apple or Google identity to an existing user with the same verified email, so no app code merges accounts. **Google (A-02.2):** `@react-native-google-signin/google-signin` shows Google's account picker on both platforms and returns an ID token for `signInWithIdToken`. It needs OAuth client IDs (`EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` on both platforms, plus `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` on iOS, whose reverse is the iOS URL scheme the config plugin adds). Without them the button is hidden and the plugin is left out. Supabase skips the nonce check for Google, because Google's iOS SDK puts a nonce in the token that the app can't see. Sign-out also signs out of Google on the device. A name from the provider fills an empty profile display name (FR-AUTH-4); otherwise onboarding asks. A cancelled sign-in returns to S-02 with no message.
- **Signed-in state in the app:** `AuthProvider` (`src/features/auth/session.tsx`) follows `onAuthStateChange`, and the root layout keeps the splash screen up until the saved session is read (S-01). The layout's `Stack.Protected` guards show `(auth)` (sign-in and code entry) only while signed out and `(tabs)` only while signed in, so a sign-in or a sign-out (including a revoked refresh token) moves the user without manual redirects. The code screen keeps the pending email in the device's drafts store, so it survives the app being killed, and counts wrong codes (5 at most). The magic link opens `auth-callback`, which reads the tokens from the URL fragment. On first sign-in the profile's locale is set from the device (FR-AUTH-4). Sign-in needs a network connection: offline, the screens show the offline banner and disable their buttons.
- **Onboarding guard:** `HouseholdProvider` (`src/features/household/membership.tsx`) reads the signed-in user's active membership and caches its IDs and settings on the device (removed at sign-out), so a member opens straight into the app offline. The root layout shows `(onboarding)` only to a signed-in user with no household, and `(tabs)` only to a member. A new device offline with no cached membership shows a retry screen. Onboarding answers and the current step are a draft (`useDraftState`), so an interrupted onboarding resumes where it stopped (FR-ONB-7). The household's region sets the app's locale.
- **Sign-out (FR-AUTH-7):** `signOut()` in `src/features/auth/sign-out.ts` runs every cleanup registered with `onSignOut()`, clears all drafts, then deletes the session on the device and asks the server to revoke the refresh token, which works offline. Modules that keep data on the device register a cleanup: the sync layer for its encrypted copy of household data, and notifications for this device's push token.
- **Biometric unlock:** `expo-local-authentication` locks the app over an existing session. It isn't a sign-in method. `BiometricLock` (`src/features/biometric`) wraps the signed-in app. The setting is per device, off by default, with a timeout of immediately, 1, 5 or 15 minutes (default 5). It's saved in the device's key-value store with the time the app last went to the background, and both are cleared at sign-out. When the lock is on, a cold start or a return after the timeout shows S-04 over the app, which hides it from screen readers too, and it also covers the app in the app switcher. The system prompt falls back to the device passcode. If the device has neither biometrics nor a passcode any more, the lock turns itself off with a notice. The switch is on the Account screen (S-31), and sign-out is there too. The Household tab (S-25) is a hub that opens members, people, settings, privacy and data (S-30) and Account.
- **Session storage:** encrypted (F-08). `createEncryptedStorage` in `src/lib/encrypted-storage.ts` gives each storage key a random AES-256 key, stored in `expo-secure-store` and readable after first unlock, and seals the value with AES-GCM from `expo-crypto`. Only the ciphertext goes to SQLite storage (`expo-sqlite/localStorage`), which avoids SecureStore's size limits. Removing the item (sign-out) deletes both the ciphertext and the key. Data without its key, or data that fails authentication, reads as signed out and is cleared. A SecureStore error is passed on rather than treated as a sign-out. supabase-js reads the session before every request, so each value is read from SecureStore at most once per launch, with overlapping reads sharing it, and then served from memory, which writes and removals keep current. Otherwise the first sync's parallel pulls each read the Keystore, and one failed read could delete the session without Supabase noticing, leaving the app signed in but every request `anon` (#336). **No device backups (SR2-L1):** `android.allowBackup` is `false` in `app.config.ts`, so Android Auto Backup never copies the app's files, databases or key-value store (household ID, device calendar state) to Google Drive, and never restores a sealed session without its Keystore key. Everything the app needs is on the server.
- **Account deletion (A-04.3, FR-PRIV-3):** in the app, which Apple requires. `delete_account()` needs a sign-in in the last 10 minutes, read from the token's `amr` sign-in times, so the app has the user sign in again (email code, Apple or Google) first and checks it's still the same account. If nobody who could keep the household would remain, the household goes too (the FR-HH-8 rule); the last parent with others is refused until they promote someone or delete the household (FR-HH-14); otherwise the household carries on without them. `account_deletion_preview()` tells the confirmation which of these applies. Store subscriptions aren't cancelled: the app links to the store.
- **Household deletion (FR-PRIV-7):** `request_household_deletion()` deletes at once when the caller is the only parent. With two parents it records a request in `household_deletion_requests`, which every member can read, and the other parent has 7 days to `confirm_household_deletion()`; either parent can `cancel_household_deletion()`. Asking and confirming both need a recent sign-in. Push notifications for the request come with N-01.

### Notifications

- **Push:** `expo-notifications` and the Expo push service. Tokens are stored in `push_tokens`, one row per device, written only through `register_push_token()` (which moves a token to whoever signs in on the device next, keeping at most 10 per user) and removed at sign-out with `unregister_push_token()`. `PushRegistration` (`src/features/notifications`), mounted in the tabs layout, registers the token at launch, on returning to the foreground and when it changes, but only when permission is already granted.
- **Permission in context (FR-NOT-2, FR-ONB-8):** nothing asks at launch or in onboarding. The first time this device's own change plans a week (the `week_planned` moment), `usePushPrompt` shows a sheet that explains before the system asks, once per member per device and only while the system can still ask. Notification settings (S-29) can turn push on too, and a denied permission shows "off in system settings" with a link there. Android uses one silent channel (`default`); nothing plays a sound (FR-NOT-6).
- **Sending:** the `notifications` table is both the in-app inbox and the push queue. `private.enqueue_notification()` creates a member's notification if their switch for the type is on; push types get `deliver_at`, now or the end of their quiet hours, and inbox-only types (household changes) get none. Every minute `pg_cron` runs `private.dispatch_pushes()`, which, when pushes are due and the Vault secrets `notify_function_url` and `notify_cron_secret` exist, calls the `notify` Edge Function through `pg_net`. `notify` checks the shared secret (`NOTIFY_CRON_SECRET`; JWT checking is off for it), claims due rows with `claim_pushes()` (service role only, which drops members who left or turned the type off since), and posts one silent message per device to the Expo push service (`channelId` `default`, `sound: null`, `categoryId` for "turn off this type"). A refused batch is handed back with `release_pushes()`; devices Expo reports as `DeviceNotRegistered` are dropped. Messages carry the notification's ID and type only.
- **"Plan your week" (FR-NOT-3):** every 5 minutes `pg_cron` runs `private.enqueue_plan_week_reminders()`. For each parent and family member with the type on (caregivers can't change the plan), `private.plan_week_due()` works out the household's coming week and when its reminder is due: by default the day before the week starts at 18:00, or the member's own day and time, in the household's timezone. A reminder due up to 6 hours ago is queued once per member and week (dedupe key `plan_week:<week start>`) unless `private.week_is_planned()` finds 5 or more dinner days in that week (FR-PLAN-12); one due longer ago is skipped rather than sent late.
- **Quiet hours and controls:** quiet hours and per-type settings are enforced on the server before sending. `notification_prefs` holds one row per member, written by the member on S-29; no row means the defaults (every type on, "plan your week" at 18:00 the day before the week starts, quiet hours 21:00 to 07:00). Times are minutes after midnight in the household's timezone. `private.notification_prefs_of()` reads a member's settings with the defaults filled in, and `private.quiet_hours_release()` gives the time a push due inside quiet hours may go: the end of quiet hours, local to the household. The app keeps the last settings it saw on the device for local notifications.
- **Copy:** notification text is localized on the server, chosen by the recipient's locale (the profile's, else the household's). It comes from `notifications.messages` in the app's locale files, through `supabase/functions/notify/copy.json`, which `pnpm run notify:copy` generates and CI checks. Push copy has no placeholders, so nothing personal can be filled in (FR-NOT-9).
- **In-app inbox (S-24):** the `notifications` table, read only by its member and written only by the server; it keeps the last 50. The bell in the Plan tab's header shows the unread count and opens `/plan/inbox`. Tapping an entry, or a push, calls `mark_notifications_read()` (so it reads as read on every device) and opens the related screen. `NotificationResponses`, in the tabs layout, registers the "turn off this type" category for each type and handles taps, including the one that launched the app. Household changes (a member joining or leaving) come from a trigger on `household_members` and say what happened, not who. Development and preview builds can send the member a test push from S-29 (`send_test_notification()`, one a minute).
- **Email:** sent through Resend, for invitations and, later, digests.
- **"List is ready" (FR-NOT-4):** `announce_list_ready(week, source)` tells the household's other members, through `enqueue_notification()`, that the list for that week is ready. The List tab's button calls it (`button`), and so does the device whose own change plans the week (`week_planned`). `list_ready_events` (one row per household, week and local day) makes it at most once per list per day, whichever comes first, and lets the button say it was sent today.
- **"Defrost tonight" (FR-NOT-5):** local notifications, scheduled by `DefrostScheduler` in the tabs layout from the synced plan. Each live dinner in the next 14 days whose recipe has `tag.needs_defrosting` gets one at 08:00 device time (spec AS-7), or at the end of quiet hours if they cover 08:00, naming the meal. The scheduler reconciles the device's scheduled notifications (IDs `defrost.<entry>`) whenever the plan, recipes or settings change and when the app returns to the foreground, so a moved or removed entry moves or cancels its reminder. Nothing is scheduled while the type is off or permission isn't granted, and sign-out cancels them.
- **Phase 2 notifications.** `notification_prefs` gains `calendar_reminders`, `event_changes`, `who_taking` and `document_expiry`.
  - **Event reminders (FR2-REM-2):** local, like "defrost tonight". An `EventReminderScheduler` (tabs layout) schedules the reminders of visible events for the next 14 days from the synced copy (`eventReminderSchedule()`, IDs `event.<event>.<date>.<offset>`). All-day events count back from 09:00 household time (PROPOSED). Reminders other than "at the time" that fall in quiet hours (household time) move to their end, and are dropped if that's after the start. On Free, or after a lapse, only each event's first reminder (earliest `created_at`) is scheduled; the tier last seen is kept on the device so this works offline. iOS keeps at most 64 pending local notifications per app, so both schedulers hand their lists to `setLocalNotifications()` (`local-budget.ts`), which keeps the nearest 60 across both and reconciles them, refilled on start, foreground and sync. Text names the kind, time and taking member; "show event details" (S-29, kept per member on the device, off by default) adds the title and place. Notes and people never appear.
  - **Server types:** `event_changed` (Premium; a trigger on `events` and one on `event_exceptions` enqueue it for the other members who can see the event when a member creates, moves or cancels an event or occurrence in the next 14 days, deduplicated per event and hour; server writes tell nobody), `who_taking` (`private.enqueue_who_taking()` every 5 minutes: from 18:00 to 21:00 household time, each parent gets one per untaken appointment occurrence tomorrow) and `document_expiring` (Premium; `private.enqueue_document_expiry()` every 5 minutes: from 09:00 to 12:00 household time, each parent gets one for each ready document expiring in 30 or 7 days, PROPOSED; the payload is the category and date only, with no category for `doc.medical`, and nothing is pushed after a lapse). Repeats stay a device job (R2-CAL-1), except that `private.event_dates()` repeats the device's rule to list the dates a series starts on in a short range. `claim_pushes()` checks again before sending: a change push needs Premium and that the member can still see the event (`private.member_can_see_event()`), a prompt needs a parent and the occurrence still untaken. Payloads carry IDs, kinds, the change and dates only; titles appear only in local notifications when the member allows it (FR2-REM-3). Calendar pushes add the event ID and occurrence date to the message data, so a tap opens the event; "who's taking?" taps carry `prompt=push|inbox` for `who_taking_prompt_answered`.

### Environments

| Environment | Supabase                                                                                          | EAS build profile and environment | Update channel | App ID                        |
| ----------- | ------------------------------------------------------------------------------------------------- | --------------------------------- | -------------- | ----------------------------- |
| Development | Hosted `parent-manager` for builds on devices; the local stack (Docker) for sessions and CI tests | `development`                     | `development`  | `com.myparentmanager.dev`     |
| Staging     | Hosted `parent-manager` (the existing project)                                                    | `preview`                         | `preview`      | `com.myparentmanager.preview` |
| Production  | Hosted `parent-manager` until D-1; then a new project, created before the external beta           | `production`                      | `production`   | `com.myparentmanager`         |

- **Separate app IDs** let all three install side by side. `app.config.ts` reads `APP_VARIANT` (`development`, `preview` or `production`), which each build profile sets in `eas.json`; `development-simulator` inherits `development`'s. Without `APP_VARIANT` the config is production's, so EAS commands that don't run a build (submit, credentials) act on the store app, and local scripts (`pnpm run ios`, `android`, `start`) set `development`. Each variant also gets its own name suffix and URL scheme (`parentmanager-dev`, `parentmanager-preview`, `parentmanager`), so deep links open the right install. Maestro flows take the app ID as `APP_ID` and default to production's.
- **Supabase plan:** the Free plan allows two active projects per organization, and the Yakka project already uses one. Free projects also pause after a week of inactivity, which is unacceptable for production. **Decision:** Supabase Pro for production, in a new or upgraded organization.
- **One hosted project until the beta (decided 2026-11-09):** to stay on the Free plan, development and preview builds share the hosted `parent-manager` project, and migrations reach it through the Migrations workflow after each merge. Automated tests (sessions and CI) use the local stack, never the hosted project. It holds test data only: no real family data, no backups, and it pauses after 7 days without activity. Since 2026-11-12 production builds use it too: all three EAS environments set `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` to `parent-manager`, so nothing that needs an EAS environment waits on D-1. Giving production its own project (F-03.2, #10) waits for D-1, and must happen before any real family uses a production build.

### CI/CD

- **On every PR:** lint, formatting, types, unit tests and an Expo dependency check, plus pgTAP database tests against a local Supabase stack ("Database tests", F-04.1), Deno tests for Edge Functions ("Edge Function tests", F-04.2) and the two-device sync harness ("Sync harness", H-06.3).
- **On `main`:** E2E with Maestro on Android (an emulator on Linux) and iOS (a simulator on a macOS runner, which is free for a public repo, with Xcode 26.4 or later, F-04.3). Both jobs live in `.github/workflows/e2e.yml`, build the production variant as a release, and can also be started on any branch with `workflow_dispatch`.
- **Database migrations:**
  - **Staging:** `.github/workflows/migrations.yml` applies them after any merge to `main` that changes `supabase/migrations`, usually within 5 minutes (F-04.4). It prints a dry run, then runs `pnpm supabase db push --remote=<ref> --yes`. The "staging" GitHub environment holds a `SUPABASE_ACCESS_TOKEN` secret (a token scoped to the staging project) and a `SUPABASE_PROJECT_REF` variable, both added by the product owner.
  - **Production:** the same workflow, started by hand with target "production". The "production" GitHub environment requires the product owner's approval before the job runs, and holds that project's token and ref. Until the production project exists (D-1), the job stops with a message saying what's missing.
  - **No hand-applied migrations:** apply to hosted projects only through this workflow, so its history and the repo stay in step.
- **Builds and updates:**
  - **Preview builds:** EAS builds them on demand.
  - **Over-the-air updates:** with `expo-updates`, the runtime version is a fingerprint of the native code. Each build profile in `eas.json` has its own channel (`development`, `preview`, `production`). Because the app config is part of the fingerprint, updates are published with the target builds' `APP_VARIANT` (`pnpm run update:preview`). JavaScript-only fixes go out as OTA updates to `preview`, and to `production` only with the product owner's approval.
  - **Store builds and submissions:** these need approval (a human gate).

### Observability

- **Sentry** (`@sentry/react-native` with its Expo plugin):
  - **What it captures:** crashes, performance traces and source maps uploaded from EAS builds.
  - **Privacy settings:** `sendDefaultPii: false`, a `beforeSend` that strips user content, and the user ID only.
  - **Wrapper (F-07.1):** `src/lib/crash-reporting.ts`. Without `EXPO_PUBLIC_SENTRY_DSN` it does nothing (D-4), so turning Sentry on needs only EAS environment variables. Events lose request data, extras, unlisted contexts and the device name; messages lose emails, double-quoted text and Postgres key details; URLs lose their query and fragment; console breadcrumbs are dropped. Screenshots, view hierarchy and replays are off, and 20% of sessions send traces.
  - **Turning it on:** set `EXPO_PUBLIC_SENTRY_DSN` (plain text) in each EAS environment. For readable stack traces, also set `SENTRY_ORG` and `SENTRY_PROJECT` (plain text) and `SENTRY_AUTH_TOKEN` (secret), then make new builds; without the org and project the plugin skips the source-map upload (`app.config.ts`). After `pnpm run update:preview`, run `pnpm exec sentry-expo-upload-sourcemaps dist` with `SENTRY_AUTH_TOKEN` set to upload the update's source maps.
- **PostHog:**
  - **Events:** carry only IDs, counts and fixed values, never names or content.
  - **Session replay:** off.
  - **Region:** US data region at launch. EU hosting can be reviewed for the UK.
  - **Uses:** activation and retention funnels from the vision's metrics, plus feature flags.
  - **Wrapper (F-07.2):** `src/lib/analytics`. `track(event, properties)` takes only events in the schema (`schema.ts`, one entry per event in spec section 3), with each property an ID (UUID), a count, a duration, a flag, a value from a fixed set, or a fixed lowercase code. It checks them again at runtime and drops, and reports by name only, anything that doesn't fit. A `before_send` filter drops SDK events we don't send (screens, lifecycle) and properties that could identify someone (`$device_name`, URLs, person properties). GeoIP, autocapture and surveys are off. `AnalyticsIdentity` identifies the user by ID and registers `household_id`, `role`, `tier`, `region` and `locale`; `platform` and `app_version` are always set.
  - **Offline:** the SDK keeps its queue in expo-sqlite's `localStorage` and keeps events after a network error, so they send once the device is back online.
  - **Opt-out (FR-PRIV-5):** `setAnalyticsOptOut` stores the choice on the device (`analytics.opted_out`), even while PostHog is off, and stops every event. It survives sign-out. The setting's screen is A-04.1.
  - **Turning it on:** without `EXPO_PUBLIC_POSTHOG_KEY`, nothing is sent (D-4). Set it, and optionally `EXPO_PUBLIC_POSTHOG_HOST` (default `https://us.i.posthog.com`), as plain-text EAS environment variables. The project key is public by design.
- **Forced updates and kill switches:** these live in `app_config` in Supabase rather than PostHog, so they work even if analytics is blocked.
  - **Keys (F-09):** `app.minimum_version` (`{"ios": "1.2.0", "android": "1.2.0"}`, or one string for both), `app.store_url` (`{"ios": …, "android": …}`; Android falls back to its Play listing) and `app.kill_switches` (`{"ai_import": true, "export.pdf": true}`; true turns that feature off). Switch names are in `KILL_SWITCHES` (`src/lib/remote-config.ts`): `ai_import` and one per export target. Change them with SQL on the hosted project, for example `insert into app_config (key, value) values ('app.kill_switches', '{"ai_import": true}') on conflict (key) do update set value = excluded.value;`.
  - **In the app:** `RemoteConfigProvider` reads the keys at launch, on reconnecting and on returning to the foreground, with a 5-second timeout. A failed read keeps what the app has, so offline it always opens (fails open). Kill switches are cached on the device, so a feature that was off stays off on the next launch; the minimum version isn't. `ForcedUpdateGate` shows S-01's update screen in place of the whole app while `expoConfig.version` is below the minimum. Features wrap entry points in `<FeatureGate feature="ai_import">` or check `useFeatureEnabled()` (AI-20: manual entry stays).
- **Supabase:** its logs cover the database and Edge Functions, with alerts on webhook failures and AI cost.

### Localization

- **Libraries:** `i18next` with `react-i18next`, which Expo's guide lists, and `expo-localization` for device settings. `Intl` (supported by Hermes) handles plurals, numbers, dates and currency.
- **Locales:** `en-US` is the base, and `en-GB` and `en-AU` override only the words that differ, such as "diapers" and "nappies".
- **Units and sections** follow the household's region. Language follows the device, falling back to the household's locale.
- **Lint rule:** ESLint rejects text written directly in JSX (`react/jsx-no-literals` with an allowlist).
- **Pseudo-locale:** a pseudo-locale in development builds lengthens text and adds accents, to catch layout and hard-coded strings.
- **Server copy:** notifications, emails, store listings, legal documents and the starter library are versioned per locale.

### Design system

- **Tokens:** `src/constants/theme.ts` holds every token in [design-system.md](design-system.md) under the same name, with `light` and `dark` color and elevation sets. Components read them through `useTheme()` (`src/hooks/use-theme.tsx`), which follows the system appearance.
- **Overrides:** `ThemeOverride` forces a scheme or an extra text scale for a subtree. Only the component gallery uses it, to preview dark mode and the largest text size side by side.
- **Text:** all text goes through `Text` in `src/components/text.tsx`, which applies a `type.*` and a `color.*` token and always scales with the system text size.
- **Fonts:** Fraunces 600 comes from `@expo-google-fonts/fraunces` and is embedded at build time by the `expo-font` config plugin, so there's no runtime font loading or splash-screen wait. Everything else uses the system font.
- **Icons:** `expo-symbols` (SF Symbols on iOS, Material Symbols on Android) behind the `Icon` component in `src/components/icon.tsx`, which names each icon once per platform and mirrors directional icons in right-to-left layouts.
- **Interrupted forms:** `useDraftState` (`src/hooks/use-draft-state.ts`) keeps an in-progress form in the `expo-sqlite` key-value store, under a `draft:` prefix, so it survives the app being killed (NFR-A11Y-8). Drafts stay on the device and are never synced. Sign-out and account deletion must call `clearAllDrafts()`.
- **Motion:** `useReduceMotion()` follows the system setting. Sheets, toasts and skeletons fade or stay still when it's on (NFR-A11Y-7).
- **Contrast:** a unit test checks every allowed color pair against WCAG 2.2 AA in both modes (NFR-A11Y-1).

## 10. Trade-offs, risks and decisions

| Topic                      | Trade-off or risk                                                                                                        | Proposal                                                                                                                            |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| Offline sync               | A library could fail our conflict needs late in the project.                                                             | Our own outbox and Realtime (D-13), held to the conflict rules by the two-device test harness in CI.                                |
| Row-level last-write-wins  | A partner's edit to the same field can be lost.                                                                          | Small, granular rows, check-offs recorded with who and when, and "updated by" hints. Revisit with CRDTs only if real users hit it.  |
| Unit merging               | Mass and volume can't merge without a density.                                                                           | Keep them as separate lines rather than guessing. Add densities for common ingredients over time.                                   |
| AI cost and abuse          | Image parsing is the most expensive call.                                                                                | Quotas, rate limits, a cost ceiling per job, and schema.org parsing first.                                                          |
| AI accuracy and allergens  | A missed allergen is a safety issue.                                                                                     | Mandatory review, allergen highlighting, a disclaimer, and an evaluation set.                                                       |
| Apple Reminders            | The public API has no sections and no ordering.                                                                          | Decided in the G-06.1 spike: one list per week, with the section in each reminder's notes (section 7).                              |
| Android export             | No native checklist target.                                                                                              | The share sheet and Copy for the MVP. Consider the Google Tasks API later.                                                          |
| Children's and health data | Legal exposure, such as UK GDPR and US state health-data laws.                                                           | Collect the minimum (age bands), no ads, and legal review before beta.                                                              |
| Device calendars           | Server sync with Google needs OAuth verification and a security assessment; iCloud has no public API.                    | Device-level copy and busy times through `expo-calendar` (D-14). Two-way sync later.                                                |
| Document security          | Host encryption means the server operator could read files.                                                              | Private bucket, 60-second links, vault lock and capture blocking (D-17). Revisit client-side encryption after review.               |
| Household entitlement      | Store subscriptions belong to a person, but ours cover a household.                                                      | Webhook-driven `household_entitlements`, with clear rules for when the purchaser leaves.                                            |
| Supabase plan              | Free limits and pausing.                                                                                                 | Pro for production (a **Decision**).                                                                                                |
| Google Play launch         | New personal developer accounts must run a closed test before production access (at last check, 12 testers for 14 days). | Start closed testing early, or register as an organization (a **Decision**).                                                        |
| Scope                      | The MVP already spans many areas.                                                                                        | Voice import, widgets, the share extension, barcode scanning, purchase recommendations and "fill my week" wait until after the MVP. |
